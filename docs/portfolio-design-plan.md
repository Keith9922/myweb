## 一、设计哲学：灵魂三原则

当前版本已经定下了"灵魂"——**晨曦色 + 薄云 + 羽毛 + 一首歌**的温柔感，这是它最珍贵的地方。如果硬塞光泽流动文字、霓虹背景、3D 卡片这些常见特效，整体调子会立刻变得廉价，从"翼をください"变成"某个 SaaS 落地页"。

正确方向：**保留诗意骨架，把"科技感/新颖感"做成反差点缀**——不是把整个页面变酷，而是在温柔的底色上，让某些关键瞬间出现"让人愣住"的一瞬。

### 原则 1：温柔做底，科技做点
底层永远是晨曦色、衬线字体、羽毛、云。所谓"科技感"只在 Hero 文字、作品集卡片、滚动转场这几个高光时刻出现，且必须用同一套配色（**禁用霓虹紫、赛博青**）。

### 原则 2：物理感，而非特效感
好的动效应该像真实物理——风、惯性、重量。延续"羽毛飘落"的思路：

- 鼠标拨动时，云会被推开
- 字会像被风吹散重组
- 滚动时羽毛跟着方向偏

而不是"鼠标 hover 卡片 3D 旋转 45 度"这种炫技。

### 原则 3：一条隐喻贯穿
整站围绕**翼 / 飞翔 / 天空**这一个意象。每个段落是天空的一种状态：

> 清晨 → 高空 → 黄昏 → 夜空

颜色、云、光线随滚动渐变。这是 godly 类站点最常见也最有效的手法。

### 原则 4：意境靠"感"不靠"说"⭐ 关键约束

整站的**底层气质**取自某种东方/日系的"克制 + 物哀 + 静谧"的美学，但**绝对不在任何地方直接写出来或用 stereotyped 符号点明**。这是 "show, don't tell"——让懂的人会心一笑，让不懂的人也觉得"很安静很美"，但谁都看不到"日系"这两个字。

**❌ 禁止（"telling"，破坏意境）：**
- 任何"日系作品集"、"和风"之类的文字标签
- 樱花、鸟居、富士山、浮世絵、和服、日式纸鹤这种 stereotyped 视觉符号
- BGM 旁标"现在播放：翼をください"歌名
- 大量日文 / 假名做装饰或界面标签
- 自我介绍里写"我喜欢日本文化"
- 直接套日本国旗红 / 抹茶绿等典型日本配色

**✅ 应该（"showing"，让人下意识感受到）：**
- **大量留白**（"間"的精神，但绝口不提这两个字）
- **配色克制**：低饱和、低对比，米白 + 淡蓝 + 灰
- **字体单一**：一种衬线字 + 偶尔的细体无衬线
- **动效缓慢**：所有过渡比常规网站慢 30-50%，让人下意识"安静下来"
- **不完整感**：羽毛飘落、风吹散字、季节流转——传达"易逝/无常"
- **音乐自己说话**：BGM 自然播放，不附带任何文字解释，懂的人自然懂
- **意象泛文化化**：用"羽毛、云、天空"这种跨文化元素，而非任何国家专属符号

**判断标准**：如果你做完一个元素，需要写"这是日式 xxx"才能让人理解它的意图——**那就是失败的**。删掉重做。

## 二、架构方案对比

讨论中出现了**两种架构**，最终倾向于"分页"方向（用户已表态认同）。

### 方案 A：单页长滚动（最初提案）

把整站做成一次"飞行旅程"，从黎明走到夜晚：

| #  | 章节                  | 天空状态           | 内容要点                                     |
| -- | --------------------- | ------------------ | -------------------------------------------- |
| 00 | 入口门 / Prelude      | 黎明前的暗蓝       | "推开这扇窗"，解锁音乐                       |
| 01 | Hero · 启程           | 清晨米白           | 标题"风吹文字"动效                           |
| 02 | 关于我 · About        | 浅天蓝             | 头像 + 自我介绍                              |
| 03 | 时间线 · 来时的路 ⭐  | 中天蓝             | 纵向飞行轨迹，云中划过的虚线，节点是经历     |
| 04 | 作品集 · Works ⭐重构 | 高空蓝             | 真实项目卡片 + 简介 + 技术栈 + 链接          |
| 05 | 技能 · Stack ⭐       | 接近黄昏           | 星图 / 羽毛云，**禁用百分比进度条**          |
| 06 | 信 · Letter           | 黄昏暖橙           | 保留现状，背景渐入暖色                       |
| 07 | 联系方式 · Contact ⭐ | 夜空深蓝（带星）   | 邮箱、GitHub、社交链接、简历下载，BGM 渐弱   |

优点：氛围连贯、音乐不打断、godly 上 95% 的个人站都这么做。

### 方案 B：门厅 + 几个房间（最终倾向）

把整站想成一栋小屋：

- **入口门**（保留）：解锁音乐，仪式感入口
- **首页 / Home**：玄关。短、快、抓眼。30 秒能说清"这人是谁、做过什么、有什么本事"。每个板块都是引子（teaser），配 `了解更多 →` 通向子页
- **About 关于我**（子页）
- **Works 作品集**（子页 + 项目详情子页）
- **Skills 技能**（子页）
- **Certificates 证书**（子页）
- **Letter + Contact 信 + 联系**（子页，合并做结尾）

导航栏：`首页 / 关于 / 作品 / 技能 / 证书 / 联系`，6 个，密度刚好。

#### 关键技术约束：用 SPA 模拟分页

如果每次点击都"白屏 → 加载新页面"，沉浸感（音乐、天空、羽毛）会断。

> **底层是 SPA，视觉上每次切页是一次完整的过场**——比如新页面像云从右边飘过来盖住旧页面，或旧页面"飞向天空"消失。

这样既享受"分页带来的清爽"，又不丢"翼をください"那个连贯氛围。

## 三、首页（Landing Page）设计

首页逻辑是 **"全家福预览"**——每个子页都在首页有一个浓缩切片，让用户不点进去也能拿到核心信息。

结构（从上到下，约 4-5 屏滚动）：

1. **Hero · 启程** — 保留 "愿有羽翼 / 向往晴空"，标题升级成"风吹文字"动效
   - **新增个人信息层**（解决访客 5 秒内不知道"这是谁"的问题）：
     - 在 Hero 标题**下方**或**右下角**加一行"低调署名"：`—— [名字] · [一句话身份]`
     - 或在导航栏左侧加一个 logo + 名字
     - **关键**：低调、小字号、不抢戏，但能扫一眼 get 到
     - 不要做"Hi, I'm XXX, Frontend Developer"这种过于直白的开头
2. **About 引子** — 左侧小头像 + 右侧三行字（身份 + 一句价值主张 + 标签），底部 `关于我 →`
3. **Works 引子** — 横向 3 张精选项目卡片（真实缩略图 + 项目名 + 一句描述），底部 `查看全部作品 →`
4. **Skills 引子** — 浓缩版技能星图，6-8 个最核心的技能/工具图标在小天空里漂浮，底部 `完整技能树 →`
5. **Certificates 引子** — 一行横向无缝滚动的证书缩略图带，底部 `查看全部 →`
6. **Footer · 信 + 联系入口** — 保留"信"的温度，短文字 + `给我写信 →`

> 信息密度反而比现版更高，因为每节都指向有内容的子页。

## 四、子页详细设计

### 1. 作品集（Works）

**这是最重要的一页。**

**布局选择（最终倾向方案 B）：**

| 方案                | 描述                                                                 | 适用场景               |
| ------------------- | -------------------------------------------------------------------- | ---------------------- |
| A · 飞鸟群（创意）  | 每个项目是一只"鸟"，散布天空不同高度，hover 展开成卡片               | 6-10 个项目，视觉冲击  |
| B · 云上画廊（稳妥） | 卡片像云一样错落瀑布流排列，hover 时投影加深，像漂浮在天上 ⭐推荐  | 任意数量，扩展性好     |

**结构：**
- 顶部一段引言（一两句话讲做项目的关注点）
- 筛选标签
- 错落瀑布流卡片：项目封面图 + 标题 + 简介 + 技术栈
- 背景：羽毛和云密度比首页大（首页是"远眺"，作品集是"飞在天空里"），可加几只 SVG 飞鸟剪影

线框图：[`docs/wireframes/wireframe_02_works.svg`](./wireframes/wireframe_02_works.svg)

### 2. 项目详情（Project Detail）

**关键交互：不跳新页面，做"卡片放大占满全屏"的效果**（类似 iOS App Store 卡片过渡）。

**结构：**
- 左上 `← 回到作品集`，右上关闭
- 标题 → 技术栈标签 → 大封面 → 背景故事（为什么做、怎么想） → 截图轮播 / Demo → 外链按钮（GitHub、在线体验、相关文章）

**打开/关闭方式：** 从原卡片位置"展开放大"，关闭时"缩回原位"，不真换页。

线框图：[`docs/wireframes/wireframe_03_project_detail.svg`](./wireframes/wireframe_03_project_detail.svg)

### 3. 技能（Skills）

**这一页可以做得最炫**——内容本身比较抽象，正好适合视觉化。

**核心：把技能做成可交互的"星图 / 羽毛云"**

- 背景：偏暗的天蓝/黛色（与首页米白对比，有进入"内层"的感觉）
- 每个技能是一颗星 / 一根发光羽毛，缓慢漂浮
- 视觉编码：
  - **大小** = 熟练度
  - **亮度** = 使用频率
  - **颜色** = 类别（前端/后端/设计/工具）
- Hover 一颗星 → 亮起，浮出小卡片：技能名 + 几年经验 + 代表项目
- 点击 → 用虚线连出该技能用过的项目，形成小星座

**避坑：** 千万不要做"技能进度条 80% 90%"。一是俗，二是没人信那个百分比怎么算的。

线框图：[`docs/wireframes/wireframe_04_skills.svg`](./wireframes/wireframe_04_skills.svg)

### 4. 证书（Certificates）

内容性质比较"硬"，**反而要克制——别让动效抢戏，证书本身才是主角**。

**布局：垂直时间线 + 卡片**
- 左侧纵向虚线时间轴，从新到旧
- 每张卡片 = 缩略图 + 证书名 + 颁发机构 + 日期 + 一句话说明
- 点击卡片 → lightbox 放大看原图
- 背景：羽毛密度降到最低，整体偏纸张质感，像被仔细收藏在相册里

> 如果证书数量多（10+），可改成网格布局更紧凑。

线框图：[`docs/wireframes/wireframe_05_certificates.svg`](./wireframes/wireframe_05_certificates.svg)

### 5. 关于（About）

是首页 About 引子的展开版。

**结构：**
- 顶部：大头像 / 个人照片（不愿意放真实头像可用剪影或插画）
- 一段长一点的自我介绍（讲故事的口吻，比首页那段更有人味）
- 简单的人生时间线："飞行轨迹"——教育、工作、关键节点
- 底部 "我喜欢的"：书 / 音乐 / 城市 / 一句话格言（让人觉得你是个活人而不是简历）

线框图：[`docs/wireframes/wireframe_06_about.svg`](./wireframes/wireframe_06_about.svg)

### 6. 联系（Contact / Letter）

整站的收尾。

**结构：**
- **上半页：** 保留"信"的设计（米黄信纸）
- **下半页：** 四个图标按钮——邮箱（点击复制）、GitHub、博客、简历下载（PDF）
- **背景：** 渐变到夜空 —— 深蓝渐变 + 几颗星 + 月亮一角
- **音效：** BGM 微微变弱，给人"夜深了，旅程结束"的收尾

线框图：[`docs/wireframes/wireframe_07_contact.svg`](./wireframes/wireframe_07_contact.svg)

## 五、交互效果分级清单

按"性价比"和"风格契合度"分三档。**别全用，全用必毁。**

### A 档 · 强烈推荐（与"翼"主题深度契合）

#### 1. 滚动驱动的天空渐变 ⭐核心
整页背景颜色随滚动位置在 **晨曦米白 → 天蓝 → 黄昏粉 → 夜蓝** 之间渐变。云的密度、羽毛的颜色也跟着变。**这是整站的灵魂效果**，免费但极其加分。godly 上"那种高级感"很大一部分来自这个。

#### 2. Hero 标题"风吹文字"
"愿有羽翼 / 向往晴空"进入时，每个字像被风从右边一个一个吹过来，落到位之后微微飘动（不是死的）。鼠标移过时，被指针经过的字会被"吹散"再回来。比 reactbits 的 SplitText 更慢、更柔。

#### 3. 鼠标驱动的视差（已有，可加强）
让云、羽毛、远近不同的元素以不同速度对鼠标做反应。鼠标快速划过时，附近羽毛会被"推开"。

#### 4. 时间线"飞行轨迹" ⭐新颖
把简历做成一条蜿蜒向下的虚线（像飞机/鸟的航迹），滚动时一只小飞鸟/羽毛沿轨迹移动，飞过哪个节点哪个节点亮起。**比任何"卡片瀑布流式简历"都好看一百倍**，且只有这种主题能做。

#### 5. 作品卡片"翻页"交互
不要 hover 3D 倾斜（太常见）。做成"卡片像信纸一样被风掀起一角"，hover 时纸边掀起、能看到下面的简介；点击则整张纸"展开"成全屏的项目详情。配合纸张的轻微纹理。

### B 档 · 锦上添花

#### 6. 滚动进度的羽毛指示器
页面右侧一根细线，当前位置是一根羽毛随滚动垂直移动。代替传统进度条。

#### 7. 自定义光标
鼠标在普通区域是小圆点，hover 到链接/卡片时变成小羽毛或圆圈包住目标。**要做得很轻**，否则会很烦。

#### 8. 副歌触发的特效 ⭐妙招
监听音乐进度（或设个时间点），《翼をください》副歌响起的那一瞬，让页面短暂"亮一下"——所有羽毛瞬间向上飘、云被推开、远处天空稍微变亮。**一次性效果，整次访问只触发一两次，但触发到的人会记一辈子**。

#### 9. SVG 手绘装饰线
关键章节标题旁画 SVG 描出来的细线（鸟、羽毛轮廓、云朵），用 `stroke-dasharray` 做"自动绘制"动画。godly 上这种东西特别多。

#### 10. 技能"星图"
就是 Skills 子页那套：技能不用进度条，做成漂浮在小天空里的若干光点/羽毛。

### A 档 · 追加（这一轮新加的"再多一点动效"）

#### 11. 章节进入：上飘 + 渐显 ⭐免费高分
section 进入视口时，内容从下方 8-12px 处轻轻"飘起"到位 + 透明度 0→1。比硬切自然得多，几乎免费。

#### 12. 滚动方向影响羽毛飘动
向下滚 → 羽毛飘下速度加快（"风"的感觉）；向上滚 → 羽毛短暂逆向上飘。物理感再加一层。

#### 13. 子页过场（云朵覆盖）
切子页时，新页面像一片云从右边飘过来盖住旧页面，旧页面"被风带走"。不要每次都重过场——只在从首页第一次进子页用一次"仪式感"过场，之后切页用 200-300ms 的轻淡入淡出。

#### 14. 序曲（首次访问用一次）
首次进入网站不直接看到首页，先 3-5 秒极简序曲：纯色米白 → 一只羽毛缓缓飘落 → 落到中间停住淡出 → 页面"撑开"。右上角永远有 `跳过 →` 按钮。
**只触发一次**（用 localStorage 记忆），重复访问不出现。

### B 档 · 追加

#### 15. 链接 hover "一笔写出"下划线
鼠标移到链接上，下划线像一笔从左到右"写"出来（`stroke-dasharray` 动画）。比常见的 hover 颜色变化更有书写感，契合衬线字体。

#### 16. 图片"显影"加载
图片懒加载时不直接出现，而是从模糊渐变清晰（`filter: blur(20px) → 0`），像照片在显影液里慢慢浮出。

#### 17. 导航栏滚动方向感知
向下滚 → 导航栏淡出（让位给内容）；向上滚 → 导航栏淡入（你想找东西，它出现）。

#### 18. 数字"翻牌"
任何带数字的地方（年份、项目数、技能年限）出现时数字像翻牌一样滚到位。**让人感到"用心做过"**。

#### 19. 章节标题"自动书写"
关键章节标题用 SVG 文本，stroke-dasharray 做一笔一画的 calligraphy 效果，1.5-2 秒画完。

#### 20. 404 页面也要做
"你飞偏了一点"——一只剪影小鸟在云里迷路 + 一句温柔的话 + `回到主巢 →` 按钮。99% 的人不会触发，触发到的会发推安利你。

## 十一、博客页（新增 · 第 7 个子页）

### 决策：以飞书文档为内容源

不用自建 markdown 渲染器（Decap 已能编辑 markdown，但写长文章不如飞书顺手）。每篇博客在 admin 里只填一组元数据 + 飞书文档分享链接。

### 数据模型

```yaml
- name: "blog"
  label: "博客"
  folder: "content/blog"
  fields:
    - title           # 文章标题
    - date            # 发表日期
    - cover           # 可选封面
    - summary         # 一两句话引子（首页/列表用）
    - tags[]          # 标签
    - feishu_url      # 飞书分享链接
    - embed_mode      # "inline" | "external"
    - featured        # 是否首页推荐
```

### 双模式渲染

**模式 A：inline（页面内嵌）**

```html
<iframe src="{feishu_url}" width="100%" height="80vh" frameborder="0"></iframe>
```

注意：飞书文档的 X-Frame-Options 由该文档/组织的设置决定。如果嵌入失败，前端会捕获 iframe `onerror` 或加载超时，自动 fallback 到模式 B。

**模式 B：external（点击新窗口打开）**

页面只渲染一张"封面卡片"+ 标题 + 摘要 + 一个 `打开飞书阅读 →` 大按钮。点击 `target="_blank"` 跳转。

### 页面结构

- `/blog` — 博客列表页：卡片瀑布流（cover + title + summary + date + tags）
- `/blog/[slug]` — 单篇详情页：根据 embed_mode 走 inline 或 external
- 首页加一个"近期博客"引子区块（链接到 `/blog`）

### 验证结论（已实测）

用 `https://my.feishu.cn/wiki/...` 测试：
- ❌ Inline iframe 嵌入失败（白屏 + 损坏图标）
- 直接 curl 返回 403（需登录态）
- 即便有 cookie 大概率仍被 `X-Frame-Options: SAMEORIGIN` 卡住

**实施策略**：默认 external 模式。inline 模式在 schema 中保留为选项，但前端做"智能 fallback"——
- iframe 8 秒未加载完 → 自动转为 "打开飞书阅读 →" 按钮
- 用户感知不到失败

### 内容模式约束

- 博客内容写在飞书 → 网站只是入口，不存正文
- 优势：在飞书写作体验好，多端同步，不用迁移
- 代价：用户读的时候得依赖飞书的可访问性

## 十二、副歌触发特效（已确认要做）

### 技术挑战

网易云音乐 iframe 是跨域的，**无法读 audio 元素当前播放时间**。所以"歌曲到副歌时触发"这件事必须用**定时器**而不是真的监听音频。

### 实现思路

```
用户点击 "进入" 按钮 → loadMusic() 开始
   ↓
  同一时刻设定一个 setTimeout(triggerChorus, OFFSET_MS)
   ↓
  OFFSET_MS = 副歌进入的时间偏移，需要根据具体曲目实测填
   ↓
  对《翼をください》(林原惠美版) 大约是 ~50-65 秒
```

OFFSET_MS 可放进 `content/site.json`：

```json
{
  "music_id": "2163191091",
  "music_chorus_offset_ms": 58000
}
```

### 副歌触发的瞬间发生什么

3 秒内的复合动画：

1. **0-300ms**：所有羽毛瞬间反向（向上飘）+ 加速 2x
2. **300-1000ms**：天空整体亮度 +12%（CSS filter `brightness(1.12)`）
3. **0-2000ms**：远处地平线（如果有）出现一道光
4. **0-3000ms**：所有 0.85 透明度的元素（云、装饰）渐变到 1.0 再回 0.85
5. **3000ms 后**：恢复正常

整次访问只触发一次。如果用户跳过 gate 直接刷新（用了 sessionStorage 跳过）也只算一次。

### 边界处理

- 用户点了 gate 但没让音乐真的播（比如静音了）→ 仍触发视觉效果（不影响）
- 用户在副歌触发前关闭页面 → 没事
- 用户切到了别的子页 → 切页时 sessionStorage 记录"是否已触发"，避免重复

## 十、内容管理（Admin / CMS）

### 决策：本地专用后台（Local-only Admin）

经过对方案的取舍：

1. ~~自建前后端（登录 + DB + API）~~ → 砍掉，运维成本远超收益
2. ~~公网部署 Decap CMS + GitHub OAuth~~ → 砍掉，OAuth 太重
3. ~~公网隐藏路由 + 密码~~ → 砍掉，源码可读，"隐藏"是假的；且需要随时随地用手机改的场景不存在
4. **本地专用后台** ⭐ → **采用**

### 核心思路

> **后台只在本地电脑跑，公网不存在 admin。** 编辑完一键自动 commit + push，线上自动部署。

```
本地电脑：
  npm run admin
  → 自动启动 Decap 本地代理 + dev 服务器
  → 浏览器打开 http://localhost:8000/admin
  → 漂亮的 CMS UI（项目列表 / 新建 / 编辑 / 删除）
  → 保存 → 直接写入本地 markdown/JSON 文件
   ↓
git push（手动或脚本自动化）
   ↓
线上 Netlify/Vercel 自动重新部署
   ↓
1-2 分钟后线上更新
```

### 为什么这是最优解

| 维度 | 评价 |
|------|------|
| **安全风险** | **0**。admin 永不上线，攻击面是空的 |
| **账号 / 密码** | **完全不需要**。没有 OAuth，没有登录框 |
| **月费** | ¥0 |
| **运维** | 0。GitHub 帮你管数据，Netlify 帮你管部署 |
| **开发量** | 一个 YAML 配置定义内容结构，admin UI 是现成的 |
| **能力上限** | 创建/编辑/删除项目、上传图片、富文本编辑、字段验证全都有 |
| **唯一限制** | 必须在自己电脑上改（已确认这正是常态） |

### 技术实现要点

**用 Decap CMS 的 `local_backend` 模式：**

- Decap CMS 官方支持本地后端模式
- 启动 `npx decap-server`（官方提供的本地代理，监听 `localhost:8081`）
- admin UI 检测到 local_backend 配置后**完全跳过登录**
- 直接读写本地文件系统

**关键配置（`admin/config.yml`）：**

```yaml
local_backend: true       # 关键：本地模式，禁用 OAuth
backend:
  name: git-gateway       # 占位符，本地模式下不实际生效
media_folder: "images/uploads"
collections:
  - name: "projects"
    label: "项目"
    folder: "content/projects"
    create: true
    fields:
      - { label: "标题", name: "title", widget: "string" }
      - { label: "日期", name: "date", widget: "datetime" }
      - { label: "封面", name: "cover", widget: "image" }
      - { label: "技术栈", name: "stack", widget: "list" }
      - { label: "简介", name: "summary", widget: "text" }
      - { label: "详情", name: "body", widget: "markdown" }
      - { label: "外链", name: "links", widget: "list", fields: [...] }
  # ... certificates / skills / about / site
```

### 内容数据模型

需要把原本"硬编码在 HTML"的内容拆出来变成数据：

| 类型 | 字段 | 文件位置 |
|------|------|----------|
| **Project（项目）** | 标题、封面图、技术栈、简介、详情 markdown、外链、日期 | `content/projects/*.md` |
| **Certificate（证书）** | 名称、颁发机构、日期、缩略图、原图、说明 | `content/certificates/*.md` |
| **Skill（技能）** | 名称、类别、熟练度、年限、关联项目 ID | `content/skills.json`（统一一个文件） |
| **AboutMe** | 头像、自我介绍、时间线节点、"我喜欢的" | `content/about.md`（单条） |
| **SiteConfig** | 联系方式、社交链接、BGM 设置 | `content/site.json`（单条） |

### 一键启动脚本（可选锦上添花）

`package.json` 里加一个 npm 脚本，把多个进程串起来：

```json
{
  "scripts": {
    "admin": "concurrently \"npx decap-server\" \"npx http-server -p 8000 -o /admin/\""
  },
  "devDependencies": {
    "decap-cms-app": "^x.x.x",
    "concurrently": "^x.x.x",
    "http-server": "^x.x.x"
  }
}
```

执行 `npm run admin` → 同时启动本地代理 + 静态服务器 + 自动开浏览器到 admin 页。

### 自动 commit / push（可选）

可在 Decap CMS 之外加一个文件监听脚本（chokidar 监听 `content/` 变化 → 自动 git commit + push）。
但更稳妥的做法：**编辑完手动 `git push`**，避免临时草稿被自动推上线。

### 生产环境的 admin 安全

只需在 `index.html` 之外，**部署时不要把 `admin/` 目录上传到公网**——
通过 `.gitignore` 屏蔽，或在部署配置（Netlify `_redirects` / `netlify.toml`）里 deny 掉 `/admin/*` 路径。

> 双重保险：本地模式即便不小心上线，没有 decap-server 跑着也不能写文件，但仍然别让 admin UI 暴露在公网。

### 部署方案

- **托管平台**：Netlify / Vercel / GitHub Pages 任选
- **域名**：继续用现有的，或绑自定义域名
- **CI**：push 自动触发部署，无需手动操作

1. 设计内容数据 schema（projects/certificates/skills/about/site 字段定型）
2. 创建 `admin/index.html` + `admin/config.yml`
3. 创建 `content/` 目录骨架 + 几个示例条目
4. 改造前端：从硬编码 HTML → 读取 `content/*.json` 动态渲染
5. 配置 `package.json` 的 `npm run admin` 脚本
6. 配置部署时屏蔽 `/admin/*` 路径
7. 联调：本地新建一个测试项目 → 验证文件落盘 → push → 看线上是否更新

### 备选方案（备忘）

- **TinaCMS（local mode）**：将来迁 React/Next.js 后切换，体验更现代、支持所见即所得
- **完全手写后台**：如果 Decap CMS 的 schema 满足不了某些奇特需求，可以自己写一个本地 React/Vue admin（仍只跑 localhost）

### 与前端方案的协同

| 前端技术栈选择 | 本地 CMS 推荐 |

| 保持 HTML/CSS/JS（轻量级） | **Decap CMS（local mode）** ⭐ |

## 附录：核心判断与避坑提醒

**核心判断：** 当前版本"很美，但读完之后并不真的知道你是谁、做过什么"。一个作品集站，让人**认识你 + 看到你做过的项目**是底线任务，氛围是加分项不是替代项。所以新增「时间线」+「作品集重构」+「联系方式」这三块是必须的。

**避坑清单：**
- ❌ 不要做技能进度条（俗 + 不可信）
- ❌ 不要硬塞霓虹色 / 赛博风（毁灭灵魂）
- ❌ 不要 hover 卡片 3D 旋转（太常见）
- ❌ 不要 WebGL/Three.js 大特效（太重，抢戏）
